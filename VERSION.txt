ДОБАВЛЕНО В 2.5: СБОРКА EXE ПОД WINDOWS
════════════════════════════════════════════════════════════════════════════════

  build_windows.bat        сборка в один клик, с проверками на каждом шаге
  crc_storage_writer.spec  спецификация PyInstaller
  pyi_rth_ch341.py         runtime-хук для загрузки CH341DLL
  BUILD_WINDOWS.md         инструкция и разбор подводных камней

Обычная команда «pyinstaller crc_storage_gui.py» даёт exe, который НЕ МОЖЕТ
писать в микросхему. Две причины, обе закрыты:

  1. i2cpy грузит драйвер через import_module("i2cpy.driver.ch341") —
     динамический импорт, статический анализ его не видит. Итог:
     I2CInvalidDriverError при открытии программатора.
     Решение: все модули драйверов перечислены в hiddenimports.

  2. CH341DLLA64.dll грузится по голому имени прямо при импорте драйвера.
     В onefile-сборке файлы лежат во временной папке sys._MEIPASS, которой
     нет в путях поиска DLL, — загрузка падает.
     Решение: runtime-хук находит DLL в _MEIPASS и подставляет переменную
     окружения CH341DLL с полным путём. i2cpy читает её первой.

Хук не перетирает CH341DLL, заданную пользователем, и молча ничего не
делает, если DLL в сборку не клали.

ПРОВЕРЕНО НА PYINSTALLER 6.22
  Внутрь собранного exe попадают: i2cpy.driver.ch341, i2cpy.driver.ch341.dll,
  i2cpy.driver.ch347, i2cpy.driver.abc, crc_storage_i2c, pyi_rth_ch341 и сама
  CH341DLLA64.dll. Приложение стартует без ошибок импорта. Размер ~48 МБ.

ИСПРАВЛЕНО В 2.5: СЛУЧАЙНАЯ ДРОБНАЯ ЧАСТЬ
════════════════════════════════════════════════════════════════════════════════

В 2.4 галочка «точное значение» появилась включённой по умолчанию, из-за
чего привычное поведение MT_Writer (ввёл целую часть — копейки 01–99
подставились сами) перестало работать без ручного снятия галочки.

Кроме того, поле S настройку вообще игнорировало: write_bcd_slot всегда
писал точное значение, что бы ни стояло в галочке.

Что сделано:
  • Галочка «точное значение» по умолчанию СНЯТА — случайные копейки
    работают сразу, как раньше.
  • Поле S теперь уважает настройку так же, как поле T: обе ветки записи
    идут через writer.parse_value(text, exact=...).
  • Превью перестало врать. В случайном режиме записывается не то число,
    что введено, поэтому HEX показывает диапазон, а не одно значение:
      поле T, ввод 3456   →  0x00054601 … 0x00054663
                             CRC: рассчитается при записи
      поле S, ввод 9399   →  01 99 93 00 … 99 99 93 00
    В точном режиме показывается ровно одно значение и настоящий CRC.
  • В лог записи добавлена строка о том, что дробная часть подставлена
    случайно.
  • Тест на 200 случайных значений: все попадают в 01–99, все кодируются
    в BCD, нулевые копейки не подставляются.

ГЛАВНОЕ В 2.4: ВТОРОЙ ФОРМАТ ХРАНЕНИЯ — ПОЛЕ S (BCD)
════════════════════════════════════════════════════════════════════════════════

В дампе оказалось ДВА формата. Раньше поддерживался только один.

┌──────────────────┬──────────────────────────┬──────────────────────────────┐
│                  │ Поле T                   │ Поле S                       │
├──────────────────┼──────────────────────────┼──────────────────────────────┤
│ Кодирование      │ value × 100, BIG-ENDIAN  │ BCD, обратный порядок байт   │
│ Размер записи    │ 42 байта                 │ 65 байт (0x41)               │
│ Копий значения   │ 2                        │ 4                            │
│ CRC              │ CRC-16 CCITT             │ НЕТ                          │
│ Целостность      │ по CRC                   │ по совпадению копий          │
│ Пример           │ 9442.36 @ 0x01C1         │ 9399.56 @ 0x1446             │
└──────────────────┴──────────────────────────┴──────────────────────────────┘

КАК НАЙДЕНО 9399.56
  В fixed-point это 00 0E 57 B4 — такой последовательности в дампе нет.
  Отброшены все масштабы (×1…×10000), длины 2/3/4/6/8 байт, оба порядка
  байт, float32/float64, текст, обычный BCD.

  Значение лежит в BCD задом наперёд:
    9399.56 × 100 = 939956 → цифры "00939956" → 00 93 99 56
                                обратный порядок → 56 99 93 00

СТРУКТУРА ЗАПИСИ S (65 байт)
  +00  3 байта   заголовок (01 01 44)
  +03  4 байта   значение BCD    ← копия 1
  +07  4 байта   копия 2
  +11  12 байт   нули
  +23  4 байта   копия 3
  +27  4 байта   копия 4
  +31  34 байта  нули до конца записи

  9399.56 @ 0x1446, копии по 0x1449, 0x144D, 0x145D, 0x1461

ПРО CRC У ПОЛЯ S — ПРОВЕРЕНО, НЕ ПРЕДПОЛОЖЕНО
  1. Хвост записи — сплошные нули, класть CRC некуда.
  2. Подозрительные пары байт рядом (0D 3E @0x1556, 13 18 и 08 19 в логе
     @0x2F40) прогнаны через CRC-16 в шести вариантах (CCITT-FALSE,
     XMODEM, KERMIT, MODBUS, ARC, CCITT-1D0F) по всем диапазонам до
     160 байт, в обоих порядках байт — совпадений нет.
  3. CRC самой записи всеми шестью вариантами по пяти диапазонам в
     окрестностях ±300 байт не встречается.
  Целостность держится на четырёх копиях, поэтому правка обновляет все
  четыре разом.

ЧТО ДОБАВЛЕНО
  • Слоты записей: у каждого своё смещение, значение, HEX, формат и
    кнопки «Прочитать» / «Записать». Слоты независимы.
  • Выбор формата в слоте: «T — fixed-point + CRC» / «S — BCD ×4 копии».
  • Кнопка «Найти в файле» — разбирает открытый дамп.
  • Кнопка «Найти записи» — вычитывает микросхему целиком.
  • Кнопка «+ Слот» и «✕» для ручного управления списком.
  • Галочка «точное значение» в слоте: писать введённое число как есть
    или подставлять случайную дробную часть 01–99 (по умолчанию снята,
    см. раздел про 2.5).
  • В модуле: encode_bcd, decode_bcd, find_bcd_records, patch_bcd_record,
    find_records, scan_records, read_record.
  • write_and_verify принимает offset и exact.

ЧТО БЫЛО ИСПРАВЛЕНО В 2.3: АДРЕСАЦИЯ I2C
════════════════════════════════════════════════════════════════════════════════

Симптом до 2.3:
  «Ошибка: Проверка записи не пройдена (10 попыток)»
  Чтения возвращали мусор: FFFFFFFF, 1111000000FFFFFF, 00111111000000FF

Причина (ошибка в коде, НЕ в железе):
  Модуль использовал схему адресации 24C16, скопированную из MT_Writer,
  хотя работал с 24C256. Микросхема ждала ДВА адресных байта, получала
  ОДИН, и адрес каждый раз уезжал на произвольное место.

  Доказательство: возвращаемые «мусорные» байты — это реальное содержимое
  области 0x0030-0x0040 микросхемы (00 00 11 11 11 00 00 00 FF FF ...).
  Шина работала исправно, сломана была адресация.

Различие схем:
┌──────────────────┬───────────────────┬────────────────────┐
│                  │ 24C16 (MT_Writer) │ 24C256 (наш дамп)  │
├──────────────────┼───────────────────┼────────────────────┤
│ Объём            │ 2 КБ (2048)       │ 32 КБ (32768)      │
│ Адресов на шине  │ 8 (0x50-0x57)     │ 1 (0x50)           │
│ Адрес памяти     │ 8 бит             │ 16 бит             │
│ Страница записи  │ 16 байт           │ 64 байта           │
└──────────────────┴───────────────────┴────────────────────┘

════════════════════════════════════════════════════════════════════════════════
ЧТО ИСПРАВЛЕНО
════════════════════════════════════════════════════════════════════════════════

1. 16-БИТНАЯ АДРЕСАЦИЯ ПАМЯТИ
   Один адрес устройства 0x50, адрес памяти передаётся двумя байтами
   (addrsize=16). Схема с блоками сохранена только для 24C16/08.

2. ПОСТРАНИЧНАЯ ЗАПИСЬ
   Второй скрытый баг: 42 байта писались ОДНОЙ транзакцией. EEPROM не умеет
   писать через границу страницы — адрес заворачивается ВНУТРИ страницы и
   затирает уже записанные байты. Теперь payload режется по границам
   страницы с паузой tWR (10 мс) между страницами.

3. СМЕЩЕНИЕ БЛОКА ПО УМОЛЧАНИЮ 0x01C1
   Было 0x0000 — там пусто, отсюда «Текущее значение: 0.00».
   В дампе запись реально лежит на 0x01C1:
     0x01C1  значение   00 0E 68 6C
     0x01C5  дубль      00 0E 68 6C
     0x01C9  паддинг    32 нулевых байта
     0x01E9  CRC-16     AC 55   ✓ сошёлся

4. ПРОФИЛИ МИКРОСХЕМ
   24C256 / 24C128 / 24C64 / 24C32 / 24C16 / 24C08
   Для каждой: объём, разрядность адреса, размер страницы.

5. АВТООПРЕДЕЛЕНИЕ ЧИПА — кнопка «Определить чип»
   Опрашивает адреса 0x50-0x57 и смотрит, сколько откликнулось:
     • один адрес       → 24C256/128/64/32 (16-битный адрес памяти)
     • несколько адресов → 24C16/08 (8-битный адрес + блоки)
   Дополнительно перепроверяет стабильность чтения, если в памяти есть
   содержательные данные. На пустой памяти (сплошные FF) работает только
   опрос адресов — поэтому он и сделан главным признаком.

6. ВЫБОР МИКРОСХЕМЫ В GUI
   Выпадающий список на вкладке I2C. Если у вас реально 24C16 (как в
   MT_Writer) — выберите его, программа переключит схему.

7. РАСШИРЕННОЕ ЛОГИРОВАНИЕ
   Лог теперь показывает конфигурацию (чип, разрядность адреса, размер
   страницы, смещение) и каждую записанную страницу отдельно.
