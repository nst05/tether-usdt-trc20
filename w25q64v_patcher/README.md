# W25Q64V — разбор формата лога и патчер

Реверс-инжиниринг дампа флеш-памяти **W25Q64V** (8 МиБ, вычитан программатором
CH341) двухканального логгера температуры и утилита для правки значений,
выводимых на экран.

## 1. Общая структура

- Размер дампа — ровно **8 388 608 байт** (64 Мбит), полный образ W25Q64V.
- Лог — это **кольцевой буфер** записей фиксированной длины **128 байт (0x80)**.
- Запись пишется **почасово** (плюс отдельные события); сквозной счётчик и
  Unix-время идут по возрастанию, при переполнении буфер перезаписывается с
  начала (wrap), поэтому порядок записей в файле не всегда совпадает с
  хронологией.
- Запись состоит из двух половин: **META** `[+0x00..+0x40)` — настройки прибора
  и служебный «хвост», и **DATA** `[+0x40..+0x80)` — сам отсчёт.

## 2. Карта DATA-блока

Смещения даны относительно начала DATA-блока (файловое смещение = `base+0x40`).

| Смещ. | Тип | Поле | Значение в дампе |
|------:|-----|------|------------------|
| +0x00 | u32 LE | Unix-время | почасово |
| +0x04 | u32 LE | старшее слово времени | 0 |
| +0x08 | u32 LE | счётчик записи | 1…N, +1 |
| +0x0C | float64 | **ПОКАЗАНИЕ на экране** | **1.280** и др. |
| +0x14 | float64 | не используется | 0.0 |
| +0x1C | float64 | **ПОКАЗАНИЕ, зеркальная копия** | == +0x0C |
| +0x24 | float32 | температура, канал 1 | 0…29 °C |
| +0x28 | float32 | не используется | 0.0 |
| +0x2C | float32 | температура, канал 2 | −35…29 °C |
| +0x30 | float32 | константа | −35.0 |
| +0x34 | float32 | константа | −35.0 |
| +0x38 | float32 | константа | −35.0 |

Значение `−35.0` — это признак «датчик отключён / нет данных» и одновременно
удобный **инвариант**: три подряд идущих `−35.0` (`00 00 0C C2` ×3) есть в
каждой записи и не меняются при правке, поэтому именно по ним патчер надёжно
находит границы записей (шаг записей 0x80, но фаза лога «плывёт» по объёму
из-за страничной организации флеша, так что привязка к фиксированному
смещению не годится).

## 3. Показание на экране (число 1.280)

`1.280` — это **само измеряемое показание, выводимое на экран**, а не
коэффициент. Оно хранится как `float64` **напрямую** (никакого пересчёта):
что записано — то и на дисплее. Показание продублировано в двух местах
(+0x0C и основная, +0x1C зеркало); в дампе обе копии **всегда идентичны** —
это резервирование для надёжности.

Что показание — это измерение, а не константа, видно по тому, что по всему
дампу оно принимает **реальные разные значения**:

| Показание | Записей |
|-----------|--------:|
| 1.280000  | 6939 |
| 0.662944  | 2889 |
| 0.638295  | 27 |
| 0.030413  | 23 |
| 0.000000  | 4 |
| 0.185257  | 1 |

Температура (float32 ~21.7 °C, два канала) пишется рядом как сопутствующий
параметр.

**Чтобы прибор показал любое значение X**, достаточно записать `float64(X)`
в обе копии показания (+0x0C и +0x1C). Патчер делает это одной командой
(поле `reading`). Например, `1.280 → 1.290275` кодируется байтами
`DB 8A FD 65 F7 A4 F4 3F` (little-endian float64).

## 4. Контрольная сумма — вывод (важно для правки)

В META-блоке перед `0xFF`-заполнением есть 6 «случайных» байт
(смещения +0x2A…+0x2F). Проверено:

- это **не** стандартная CRC-32/CRC-16 (ISO, BZIP2, MPEG-2, POSIX, JAMCRC,
  CRC-32C, Modbus, CCITT, XMODEM, ARC) ни по одному из диапазонов записи;
- строгая проверка над GF(2) показала, что «хвост» **не является линейной
  функцией** ни содержимого записи, ни «запись + хвост предыдущей записи», то
  есть это и **не сцепленная (chained) CRC**.

Следовательно, **правка отображаемых float-значений не ломает никакую
вычислимую по дампу контрольную сумму записи**. Сам «хвост» — это
device-side величина (сигнатура/идентификатор/nonce), восстановить её из
одного дампа нельзя; для этого нужна прошивка прибора или живой прибор.
Патчер META-блок не трогает.

## 5. Использование

### GUI (без командной строки)

```bash
python3 w25q64v_gui.py
```

Окно на `tkinter` (входит в стандартный Python на Windows/macOS; на Linux —
пакет `python3-tk`), без сторонних зависимостей. Порядок работы:

1. **Открыть дамп…** — выбрать `.bin`. В таблице появятся все записи;
   программа автоматически выделяет **текущее показание (экран)** — запись
   с самым свежим временем — и показывает **два конкретных адреса**, которые
   будут изменены (`DATA+0x0C` и `DATA+0x1C` этой записи).
2. Ввести **новое значение**. Область по умолчанию — **«Текущее показание
   (экран)»**: меняются только два места в последней записи, вся история
   остаётся нетронутой. Есть также *Выделенная запись* (клик по строке) и
   *Все записи* (с красным предупреждением и подтверждением — перезапишет
   всю историю).
3. **Применить →** — патчер меняет только показание (обе копии) и в статус-
   строке показывает, сколько байт изменено и что «прочее не тронуто»,
   плюс `verify`.
4. **Сохранить как…** — записать `*_patched.bin` и залить обратно в W25Q64V.

### CLI

```bash
# сводка по дампу (в т.ч. какие показания реально встречались)
python3 w25q64v_patcher.py info dump.bin

# список записей (или CSV)
python3 w25q64v_patcher.py list dump.bin --end 20
python3 w25q64v_patcher.py list dump.bin --csv > log.csv

# поставить показание 1.290275 во ВСЕХ записях (пишет обе копии float64)
python3 w25q64v_patcher.py set dump.bin reading 1.290275 --out patched.bin

# только в одной записи (индекс 0)
python3 w25q64v_patcher.py set dump.bin reading 1.290275 --records 0 --out patched.bin

# в диапазоне записей 10..40
python3 w25q64v_patcher.py set dump.bin reading 0.75 --records 10-40 --out patched.bin

# при необходимости — правка температуры
python3 w25q64v_patcher.py set dump.bin temp1 25.0 --records 0 --out patched.bin
```

Доступные поля для `set`:
- `reading` — показание на экране (float64, пишется в **обе** копии +0x0C и +0x1C);
- `temp1`, `temp2` — температурные каналы (float32).

### Гарантия «только показание»

Патчер меняет **исключительно** байты показания и ничего больше. Перед
записью он сохраняет исходный образ, а после правки **сверяет результат с
оригиналом байт-в-байт**: если изменился хоть один байт вне полей показания
(+0x0C / +0x1C), операция **прерывается с ошибкой и файл не пишется**.

В выводе это видно строками:

```
bytes changed  : 12 (all inside the reading field)
other data     : untouched (0 bytes changed elsewhere)
```

Время, счётчик, температуры, META-блок и device-side «хвост» остаются
нетронутыми. После записи патчер также перечитывает файл и **верифицирует**
каждое изменённое поле (обе копии показания) — `verify: OK/FAILED`. Готовый
`patched.bin` заливается обратно в W25Q64V тем же CH341.

## 6. Запись только изменённых байтов (частичная прошивка)

Перешивать все 8 МБ не нужно — можно записать только тронутые байты. Но
у SPI-флеша произвольный байт «поверх» не пишется: изменение идёт через
**стирание сектора (4 КБ) и перезапись**. Поэтому «нужные байты» на практике —
это **один 4 КБ-сектор**, где лежит показание (для текущей записи это сектор
`0x0D4000`).

**В GUI** — кнопка **«Экспорт изменённых…»** (после «Применить»). Создаёт:
- `changes.hex` — Intel HEX только изменённых байтов (с адресами);
- `changes_sector_0x….bin` — сам изменённый сектор 4 КБ;
- `changes.txt` — список адресов/секторов.

В программаторе прошиваешь **только этот сектор**: «стереть сектор» по адресу
`0x0D4000` → «записать» `*_sector_0x0d4000.bin` по тому же адресу. Весь чип
трогать не надо.

**В CLI:**
```bash
python3 w25q64v_patcher.py export original.bin patched.bin --out changes
# -> changes.hex, changes_sector_0x0d4000.bin, changes.txt
```

Intel HEX проверен: корректные контрольные суммы, `type-04` для старшего
адреса, данные — ровно две копии показания на `0x0D418C` и `0x0D419C`.

## 7. Оговорка

Разбор восстановлен из одного дампа. Отображаемые поля, алгоритм пересчёта и
вывод про контрольную сумму подтверждены на данных, но **финальную проверку
нужно делать на живом приборе**: залить `patched.bin` и убедиться, что экран
показывает ожидаемое и прибор не отвергает запись из-за device-side «хвоста».
