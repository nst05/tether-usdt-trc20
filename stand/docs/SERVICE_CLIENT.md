# Как правильно написать программу для сервисного уровня

Максимально подробное руководство: как безопасно построить ПК-программу,
работающую с сервисным уровнем прибора. «Правильно» здесь означает не «как
получить доступ», а инженерную дисциплину: сервисный уровень открывает команды
записи (CMD 07 в Info Flash и внешнюю память, сервисные подкоманды CMD 03), и
неверная запись портит калибровку или приводит прибор в нерабочее состояние.
Вся суть — в страховках вокруг записи.

> **Граница.** Ниже описаны только штатные операции со страховкой: диагностика,
> резервирование, верифицированная запись, восстановление. Подмена отображаемых
> показаний, регулировка коэффициента скорости счёта энергии и обход
> аппаратного входа P2.5 — это фальсификация учёта, а не сервис, и в правильной
> программе их нет.

---

## 0. Что такое сервисный уровень и чего программа НЕ делает

Сервисный уровень (условно «3-й») — **аппаратный**. Он включается замыканием
входа **P2.5** на землю (или внутренним флагом 0x04F2.12) и пересчитывается
прошивкой на каждый кадр (`sub_49AA` → `0x8328` → маска доступа `0x06B3`).
Подробности — в `ACCESS.md`.

Из этого следует главное для архитектуры ПО:

- Программа **не включает** сервис — его включает железо. Никакого «входа на
  уровень 3» по сети не существует, и правильная программа его не имитирует.
- Программа лишь **корректно пользуется** командами, которые становятся
  доступны, когда прибор уже в сервисе.
- Признак «сервис активен» по шине напрямую не читается (флаг 0x08B8.8 не
  попадает в ответ). Достоверный источник — состояние P2.5; программно сервис
  определяется только **функционально** (по поведению сервисной команды).

## 1. Архитектура — строго слоями

```
         Сценарии / UI
              │
   Сервисные операции         ← ВСЯ защита здесь: backup, verify, журнал
   (ServiceSession)
              │
   Протокол команд            ← CMD 01/03/06/07/08, коды ошибок, длины
   (Stand)
              │
   Транспорт                  ← кадр, CRC-16/MODBUS, тайм-ауты, RS-485
   (Stand._serial)
```

Транспорт (`stand.py`) уже готов и проверен. Сервисный слой (`service.py`)
строится **над** ним и никогда не формирует кадры записи напрямую — только через
страхующие методы.

---

## 2. Пять обязательных правил (это и есть «правильно»)

| № | Правило | Почему |
|---|---|---|
| 1 | **Read-before-write** | Без снимка «до» нельзя ни проверить результат, ни откатиться. |
| 2 | **Backup зеркал** | Пароли/коэффициенты хранятся в основной и резервной копиях (сдвиг 0x0100). Читать и сохранять обе. |
| 3 | **Verify-after-write** | После записи прочитать обратно и сравнить. Не совпало — стоп. |
| 4 | **Контрольные суммы** | Info Flash защищён checksum, пароли — XOR от 0xF0. Нарушишь — прибор уйдёт в резерв или отвергнет блок. |
| 5 | **Подтверждение + журнал** | Каждая запись — с явным подтверждением оператора и полным логом кадров TX/RX. Слепых пакетных записей быть не должно. |

В `service.py` правила 1, 3, 5 встроены: `safe_write()` отказывается работать без
`backup()` и всегда делает обратное чтение; все кадры пишутся в журнал.

## 3. Жизненный цикл сеанса

```
1. connect + автопоиск скорости/чётности        (Stand / find_stand)
2. test_link                     — связь есть    (CMD 00)
3. login(password, level)        — если нужен уровень 1/2 (CMD 01)
4. probe_service()               — убедиться, что прибор в сервисе
5. backup()                      — снять и сохранить состояние «до» на диск
6. [подтверждение оператора]
7. safe_write(...)               — ОДНА штатная операция + верификация
8. повтор 6–7 по мере надобности
9. logout / close                — журнал закрыть
```

Никогда не начинайте с шага 7. Backup (шаг 5) — обязательное условие записи.

---

## 4. Определение сервиса (честно)

Чистого read-only признака сервиса в протоколе может не быть: сервисный бит
`0x06B3.2` гейтит записи, а не чтения. Поэтому `probe_service()` шлёт
сервисно-зависимую операцию и трактует ответ:

- пришли данные → **сервис активен**;
- ошибка доступа `03` (0xB84E) → **сервис неактивен**;
- иное → **определить нельзя** (положитесь на состояние P2.5).

```python
if session.probe_service() is not True:
    raise RuntimeError("прибор не в сервисе — замкните P2.5 и повторите")
```

## 5. Контрольные суммы

### Пароли (внешняя память)

Запись пароля — 6 байт значения + 1 байт контроля. Контроль — **XOR всех 6 байт
с начальным 0xF0** (не хэш):

```python
control = 0xF0
for b in password:      # 6 байт
    control ^= b
# запись валидна, если control == record[6]
```

`service.password_control()` / `password_record_valid()`. Это только формат
контроля целостности — не средство подбора. При штатной перезаписи известного
пароля пересчитайте контроль и запишите вместе со значением, иначе прибор сочтёт
запись битой и переключится на резерв.

### Info Flash

Каждый 8-словный блок Info Flash имеет 16-битную контрольную сумму. Точный
алгоритм — внутренний; при записи служебных блоков (CMD 07, коды **0xEC/0xEE**)
**прошивка пересчитывает checksum сама**. Поэтому не пытайтесь предвычислять его —
опирайтесь на обратное чтение (verify) и на то, что блок после записи проходит
внутреннюю проверку. Для быстрой сверки читаемых блоков есть `word_sum16()`.

## 6. Форматы команд записи

### CMD 07 — запись памяти и Info Flash (риск: очень высокий)

```
[ADDR] 07 [MODE] [ADDR_H] [ADDR_L] [LEN] [DATA...] [CRC_lo] [CRC_hi]
```

- `MODE` = 1 (табличные области) или 2 (внешняя память, диапазон 0x1000–0x1D3B).
- `LEN` — число байт данных; полная длина кадра проверяется как `LEN + 8`.
- Спец-коды в поле `ADDR_H`: `0xEC` — запись служебного блока Info Flash 0x1080 с
  пересчётом checksum; `0xEE` — блок 0x1090 и управление системным режимом.
- **Только после backup.** Команда способна испортить служебные блоки и пароли.

### CMD 03 — сервисные подкоманды (риск: высокий)

`[ADDR] 03 [SUBCMD] [данные...] CRC`. У каждой подкоманды своя длина и свои
диапазонные проверки — сверяйтесь с реестром 56 подкоманд (см. отчёт/`COMMANDS.md`).
Для каждой записи должна существовать **парная команда чтения** (обычно из CMD 08)
для верификации.

### Парные чтения для верификации (примеры)

| Записали (CMD 03/07) | Проверяем чтением |
|---|---|
| конфигурацию 0x04E0.. | `08 02` / `08 07` |
| сетевой адрес 0x04FE | `08 05` |
| флаги режима 0x04F4 | `08 09` |
| буфер 0x04C8.. | `08 1B` |
| 0x0420.. | `08 1C` |

## 7. Коды ошибок

| Адрес | Код | Смысл |
|---|---|---|
| 0xB842 | 01 | неверная команда/параметр или подкоманда не реализована |
| 0xB848 | 02 | ошибка записи / внешней памяти |
| 0xB84E | 03 | недостаточный уровень доступа |
| 0xB856 | 04 | запрещено текущим состоянием |
| 0xB85C | 05 | ошибка режима |
| 0xB8D0 | — | игнорирование / выход без нормального ответа |

`03` при сервисной команде — верный признак, что прибор не в сервисе (P2.5 не
замкнут). `02` после записи — тревога: проверяйте резервную копию.

---

## 8. Восстановление

Если верификация не прошла или прибор ушёл в резерв:

1. Не продолжать запись.
2. Взять сохранённый `backup_*.json` (снимок «до»).
3. По плану восстановления (`restore_plan()`) вернуть каждое поле его штатной
   командой записи и верифицировать.
4. Свериться с зеркальной копией (сдвиг 0x0100): прибор восстанавливает основную
   запись из резерва и наоборот.

## 9. Мини-пример (порядок, без реальных записей)

```python
from stand import Stand
from service import ServiceSession

dev = Stand("/dev/ttyUSB0", address=0x2A, baudrate=4800, parity="O")
with ServiceSession(dev, journal="service.log", dry_run=True) as s:
    assert dev.test_link()
    if s.probe_service() is not True:
        raise SystemExit("прибор не в сервисе (замкните P2.5)")
    snap = s.backup()                       # снимок «до» на диск
    # штатная операция + обязательная верификация:
    s.safe_write(
        write_fn=lambda d: ...,             # здесь штатная CMD 03/07
        verify_read=(0x08, 0x02),           # парное чтение
        expected=bytes.fromhex(snap.data["config_08_02"].replace(" ", "")),
        description="перезапись конфигурации")
```

Снимите `dry_run=True` только когда полностью уверены в операции и есть свежий
backup.

## 10. Чек-лист перед записью

- [ ] Прибор физически в сервисе (P2.5), `probe_service()` == True.
- [ ] Выполнен `backup()`, файл сохранён и открывается.
- [ ] Для зеркалируемых областей сняты обе копии (основная и резерв).
- [ ] Есть парная команда чтения для верификации.
- [ ] Контрольные суммы учтены (пароль — XOR 0xF0; Info Flash — пересчитает прошивка).
- [ ] Оператор подтвердил конкретное значение.
- [ ] Журнал кадров включён.
- [ ] Известен путь отката (restore из backup).

Если хоть один пункт не выполнен — запись не начинать.
