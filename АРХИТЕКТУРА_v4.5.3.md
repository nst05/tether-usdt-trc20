# Архитектура v4.5.3

```text
smt_gui.py (Tk UI)
       │ task/out Queue
       ▼
smt_backend.py (один поток-владелец транспорта)
       │
       ▼
smt_core.client.SmtClient
       │
       ├── smt_core.commands   — классификация, критичность, каталог
       ├── smt_core.protocol   — framing, decode, echo, NAME=value
       └── smt_core.transports — Serial / TCP / GSM-SMS

smt_telemetry.py ── smt_server.py ── smt_telemetry_store.py
smt_firmware.py  ── smt_state.py / smt_eventlog.py / smt_smart.py
```

## Границы ответственности

### UI

`smt_gui.py` создаёт виджеты, кладёт задания в очередь и отображает результаты. Он не открывает COM-порт и не выполняет команды напрямую.

### Backend

`smt_backend.Backend` — единственный поток, который владеет активным транспортом. Это сохраняет исходную потоковую модель v4.5.2 и исключает одновременную запись в порт из нескольких обработчиков Tk.

### Команды

`smt_core.commands.classify_command()` — единый источник истины для чтения, записи и действий. GUI, CLI, `SmtClient` и пакетные сценарии больше не имеют независимых классификаторов.

### Транспорты

Все транспорты поддерживают общий минимальный контракт `CommandTransport`: `send()`, `close()`, `is_open` и диагностические поля последнего обмена. Специальные возможности (`raw_exchange`, `send_at`, `receive_unread`) остаются доступными через конкретные реализации.

### Совместимость

`smt_client.py` переэкспортирует прежний API. Внешний код, который импортирует `OpticTransport`, `SmsTransport`, `TcpServerTransport`, `SmtClient`, `FRAMINGS`, `value_of` и наборы команд из `smt_client`, продолжает работать.

### Профиль прошивки

`smt_firmware.DEFAULT_PROFILE` содержит адреса checkpoint, главного архива и журнала событий. Парсеры используют эти значения, а не собственные разрозненные константы. Текущий профиль полностью повторяет v4.5.2.
